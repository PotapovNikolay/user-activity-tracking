## Контейнерная диаграмма

```text
                    ┌──────────────┐
   HTTP client ───▶ │     api      │ ──┐
                    └──────────────┘   │
                                       ▼
                    ┌──────────────┐  read  ┌──────────────┐
                    │  scheduler   │ ─────▶ │  PostgreSQL  │
                    └──────┬───────┘        └──────────────┘
                           │ enqueue                ▲
                           ▼                        │ write
                    ┌──────────────┐  consume  ┌────┴───────┐
                    │ Redis/BullMQ │ ────────▶ │   worker   │
                    └──────────────┘           └────────────┘

   migrate (one-shot) ──▶ PostgreSQL  (migrations + seed)
```

## 1. Цель

Собрать NestJS-приложение, подключенное к базе данных, где:

- хранятся пользователи;
- хранятся записи их активности;
- периодический cron создает задачи в очередь;
- worker обрабатывает задачи и добавляет записи активности в базу;
- пользователь может получить свой профиль и историю активности за заданный период;
- все компоненты запускаются через Docker Compose.

## 2. Архитектурное позиционирование

### Базовый выбор

Для первой версии проекта выбирается **modular monolith с асинхронной фоновой обработкой**.

В основе решения:

- одна кодовая база;
- единый bounded context с модулями `users` и `activity`;
- один основной контур хранения данных;
- разделение runtime-ролей на `api`, `scheduler` и `worker`.

### Почему это подходит для задачи

- доменная модель остается понятной;
- очередь используется по назначению;
- cron не смешивается с HTTP-слоем;
- фоновая обработка не блокирует пользовательские запросы;
- локальный запуск остается простым и предсказуемым.

## 3. Зафиксированные решения для v1

### 3.1. Серверное приложение

Основной backend реализуется на `NestJS`.

Framework задан требованиями ТЗ.

### 3.2. Модель развертывания

Система запускается как несколько процессов одной кодовой базы:

- `api`
- `scheduler`
- `worker`

Причина выбора:

- обязанности процессов разделены явно;
- HTTP-слой и фоновая обработка изолированы на уровне исполнения;
- архитектура остается цельной.

### 3.3. Хранилище данных

Основной базой данных выбирается `PostgreSQL`.

Причина выбора:

- модель данных реляционная;
- ключевой сценарий чтения — выборка активности пользователя за период;
- PostgreSQL подходит для временных диапазонов, индексов и `JSONB`.

### 3.4. Доступ к данным

В качестве слоя работы с БД выбирается `Prisma`.

Причина выбора:

- схема данных описывается явно;
- миграции и генерация типов встроены в основной workflow;
- старт проекта проще и короче.

### 3.5. Асинхронная обработка

Для очереди выбирается `BullMQ`, а в качестве backend — `Redis`.

Причина выбора:

- решение подходит под job-oriented сценарий;
- поддерживает producer/consumer модель;
- есть retries, backoff и concurrency;
- локальная инфраструктура остается простой.

### 3.6. Планирование задач

Планировщик реализуется через `@nestjs/schedule`.

Причина выбора:

- cron-логика остается внутри NestJS;
- удобно связывается с queue producer;
- достаточно для локальной и тестовой версии.

### 3.7. API-стиль

Внешний интерфейс системы строится как REST API.

Причина выбора:

- требуется ограниченный набор endpoints;
- REST проще документировать и тестировать;
- дополнительный интерфейсный слой здесь не нужен.

### 3.8. Модель активности

Активность пользователя хранится как **append-only records**.

Каждая обработанная job создает отдельную запись активности, а не обновляет агрегированную статистику.

Причина выбора:

- проще модель записи;
- проще история активности за период;
- лучше соответствует задаче трекинга.

### 3.9. Гранулярность фоновых задач

Для v1 принимается правило: **одна job на одного пользователя**.

Причина выбора:

- ретраи изолированы;
- сбой по одному пользователю не ломает всю партию;
- модель легче масштабировать.

### 3.10. Контур доставки

Фоновый поток системы:

`cron → queue → worker → database`

Это означает:

- cron инициирует работу, но не пишет активность напрямую;
- очередь развязывает producer и consumer;
- worker отвечает за обработку jobs;
- база данных получает результат фоновой обработки.

## 4. Границы системы

### Входит в v1

- хранение пользователей;
- хранение записей активности;
- cron-планировщик;
- очередь задач;
- worker для обработки задач;
- REST API на чтение профиля и активности;
- docker compose для локального запуска всей системы.

### Не входит в v1

- полноценная аутентификация и авторизация;
- распределенные блокировки;
- отдельные аналитические витрины;
- event streaming platform;
- публичная интеграция с внешними системами;
- HA-режим scheduler (несколько инстансов с distributed lock) — текущий scheduler работает как single-instance.

## 5. Компоненты системы

### `api`

HTTP-процесс, который:

- принимает REST-запросы;
- отдает профиль пользователя;
- отдает активность пользователя за период.

### `scheduler`

Фоновый процесс, который:

- запускает cron по расписанию;
- выбирает пользователей;
- ставит jobs в очередь.

### `worker`

Фоновый процесс, который:

- слушает очередь;
- читает payload job;
- генерирует запись активности;
- сохраняет запись в PostgreSQL.

### `postgres`

Основное хранилище:

- таблица пользователей;
- таблица записей активности.

### `redis`

Инфраструктурный backend для BullMQ.

### `migrate`

One-shot процесс, который:

- применяет Prisma migrations;
- выполняет seed;
- завершается до старта `api`, `worker` и `scheduler`.

## 6. Поток данных

### Основной async flow

1. `scheduler` срабатывает по cron.
2. `scheduler` постранично читает активных пользователей (`is_active = true`) keyset-обходом по `(created_at, id)`.
3. Для каждого пользователя создается отдельная job.
4. Job отправляется в очередь.
5. `worker` забирает job из очереди.
6. `worker` формирует запись активности.
7. `worker` сохраняет запись в PostgreSQL.
8. `api` возвращает данные по запросу пользователя.

### Идемпотентность

`jobId` формируется как `${userId}-${scheduledAtTimestamp}`. Это даёт дедупликацию только внутри одного cron-тика: повторное enqueue той же job в рамках того же тика BullMQ отбросит как дубликат. Два соседних тика создадут разные `jobId`.

Реальная защита от дублей — на уровне БД через unique-constraint `(user_id, source, type, ended_at)`. Он покрывает retries, повторные enqueue между тиками и race condition между worker и queue ack.

### Retry-policy и DLQ

- Транзиентные ошибки (`Timeout`, временная недоступность БД и т.п.) попадают под BullMQ retry с backoff;
- unrecoverable-ошибки (`NotFoundException`, невалидный payload) завершаются как `UnrecoverableError` и не ретраятся;
- payload и причина отказа таких jobs пишутся в отдельную DLQ `user-activity-generation-dlq`. Это сохраняет материал для разбора и ручного re-drive независимо от cleanup-политики основной очереди.

## 7. Доменная модель

### Сущность `User`

Поля:

- `id`
- `email`
- `name`
- `timezone`
- `isActive`
- `createdAt`
- `updatedAt`

### Сущность `Activity`

Поля:

- `id`
- `userId`
- `type`
- `source`
- `startedAt`
- `endedAt`
- `durationSeconds`
- `summary`
- `createdAt`

### Семантика полей активности

- `type`: тип активности, например `running`, `walking`, `workout`
- `source`: источник записи, например `system`
- `startedAt`: время начала активности
- `endedAt`: время окончания активности
- `durationSeconds`: длительность активности
- `summary`: дополнительные метрики в `JSONB` (например `steps`, `calories`, `distanceMeters`, `avgHeartRate`, `maxHeartRate`)

## 8. Схема БД

Канонический источник — [prisma/schema.prisma](../prisma/schema.prisma); ниже выдержка.

### Таблица `users`

- `id uuid primary key`
- `email varchar unique not null`
- `name varchar null`
- `timezone varchar not null default 'UTC'`
- `is_active boolean not null default true`
- `created_at timestamptz not null`
- `updated_at timestamptz not null`

### Таблица `activities`

- `id uuid primary key`
- `user_id uuid not null references users(id) on delete cascade`
- `type varchar not null`
- `source varchar not null`
- `started_at timestamptz not null`
- `ended_at timestamptz not null`
- `duration_seconds integer not null`
- `summary jsonb null`
- `created_at timestamptz not null`
- `unique (user_id, source, type, ended_at)` — идемпотентность фоновых записей

### Индексы

- `(is_active, created_at, id)` на `users` — для постраничного fan-out активных пользователей scheduler'ом;
- `(user_id, started_at desc, id desc)` на `activities` — основной keyset для чтения активности за период;
- `(user_id, type, started_at desc, id desc)` на `activities` — keyset с фильтром по типу.

## 9. API-контракты

Канонический источник схем, параметров и примеров — [openapi.yaml](./openapi.yaml).

Endpoints v1:

- `GET /users/:id` — профиль пользователя;
- `GET /users/:userId/activity?from=...&to=...&type=...&limit=...&cursor=...` — активность за период с keyset-пагинацией и опциональным фильтром по типу;
- `GET /health/liveness`, `GET /health/readiness` — служебные;
- `GET /docs` — Swagger UI.

Архитектурно значимые правила:

- `from` и `to` обязательны для чтения активности, `from <= to`, диапазон ограничен `ACTIVITY_MAX_PERIOD_DAYS` (default `31`);
- сортировка `started_at DESC, id DESC`, пагинация keyset;
- интервал `[from, to)` полуоткрытый: момент `to` не включается, момент `from` включается;
- все даты в API — ISO 8601, в БД хранятся в UTC;
- `404` при отсутствии пользователя;
- ответ activity содержит `userId`, `from`, `to`, `items` и опциональный `nextCursor`.
